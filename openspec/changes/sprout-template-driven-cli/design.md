## Context

目标是把“项目特化脚本”升级为“项目内可配置、跨项目复用”的统一 CLI。核心场景是 Agent 协同开发时高频创建文档与目录（issue/change/notes 等）。

已对齐的关键约束：
- CLI 名称：`sprout`
- 配置根目录：与 CLI 同名隐藏目录（`.sprout/`）
- 发现规则：从当前目录向上查找，命中首个配置根即停止（类 `.git`）
- 输入模式：默认参数输入，`-i/--interactive` 才进入交互
- 模板语法：纯文本 `{{name}}` 插值，不引入逻辑流
- 冲突策略（命令定义）：同一项目内命令同名时，冲突双方禁用并警告
- 冲突策略（目标路径）：可配置 `fail | overwrite | skip | rename`
- `number` 类型：支持可选 `min/max` 约束
- Agent 协同：`sprout init` 支持自定义骨架，并在项目内生成 `sprout-authoring` Skill 文档

## Goals / Non-Goals

**Goals:**
- 在任意项目中，通过 `.sprout/` 命令包快速定义并复用生成规则。
- 用统一命令 `sprout new <command>` 生成文件/目录资产。
- 提供可预测、可校验的输入与模板渲染行为。
- 让 Agent 能自动维护模板定义，降低用户手工配置成本。

**Non-Goals:**
- 不支持模板中的条件/循环/函数调用。
- 不在 v0.1 支持多层配置合并（仅首个配置根生效）。
- 不在 v0.1 处理复杂类型系统（对象数组、嵌套结构）。

## Decisions

### 1) 项目绑定发现模型（nearest-root）
- **决策**：从当前工作目录向上遍历，找到首个 `.sprout/` 即作为项目模板根；停止继续查找。
- **原因**：规则简单、可解释性高，和 Git 心智一致。
- **备选**：
  - 多层配置合并：灵活但冲突解析复杂，推迟。
  - 仅当前目录：过于严格，降低可用性。

### 2) 命令包结构
- **决策**：每个命令以目录为单位管理，位于 `.sprout/commands/<command>/`。
- **内容**：`manifest`（输入/资产声明）+ 模板文件（可空白）+ 可选示例。
- **原因**：命令级隔离，便于协作与版本管理。
- **备选**：单文件集中配置（随命令增长会膨胀）。

### 3) 输入收集与类型校验
- **决策**：默认从命令参数与 flags 提供输入；显式 `-i/--interactive` 才交互补全。
- **支持类型**：`string`、`number`、`enum`（v0.1）。
- **扩展约束**：`number` 支持可选 `min/max`。
- **原因**：优先 Agent/脚本自动化，同时保留交互模式。

### 4) 插值引擎
- **决策**：仅支持纯文本变量替换，语法 `{{var}}`。
- **原因**：降低复杂度，保证生成行为可预期。
- **备选**：Jinja 级模板（功能强但增加学习/安全/调试成本）。

### 5) 命令定义冲突与校验模型
- **决策**：启动解析阶段执行校验。
  - 命令名冲突：双方均禁用，并输出警告与修复建议。
  - 无效定义：该命令不可执行并给出定位信息。
- **原因**：避免“隐式覆盖”导致误生成。
- **备选**：就近优先/后定义覆盖（可用性高但易隐藏错误）。

### 6) 目标路径冲突策略（可配置）
- **决策**：在项目配置中声明 `conflict` 策略：
  - `fail`：直接失败（默认）
  - `overwrite`：覆盖已存在目标
  - `skip`：跳过冲突目标并继续
  - `rename`：自动重命名（追加递增后缀）
- **原因**：不同项目对“安全/效率”偏好不同，需要策略化。

### 7) Init + 本地 Skill Authoring 工作流
- **决策**：提供 `sprout init` 作为入口，支持自定义骨架；在项目内生成 `sprout-authoring` Skill 文档（不安装到全局），并可选生成示范命令包。
- **原因**：将“规范编写”从手工编辑转为可对话维护，且确保项目自包含。
- **备选**：只给 CLI，不给 Skill（不利于 Agent 协同目标）。

## Risks / Trade-offs

- **[风险] 仅文本替换能力有限** → **缓解**：在规范中预留 future 字段，为后续表达式扩展保留兼容位。
- **[风险] 用户误配 manifest 导致生成失败** → **缓解**：提供 `doctor/validate` 级别预检输出。
- **[风险] 冲突双方禁用会影响可用性** → **缓解**：错误信息明确到命令路径与冲突来源，支持快速修复。
- **[风险] `overwrite`/`rename` 可能造成非预期落盘** → **缓解**：执行前输出计划摘要（将写入/覆盖/跳过/重命名）。
- **[风险] 本地 Skill 文档与 CLI 版本漂移** → **缓解**：在 `init`/`doctor` 中提供版本提示与升级建议。

## Migration Plan

1. 在项目根执行 `sprout init`，生成 `.sprout/` 基础结构与本地 Skill 文档。
2. 按项目需求选择空骨架或示范命令包，并补全自定义模板。
3. 将现有项目特化脚本中的模板/命名规则迁移为命令包定义。
4. 使用 `sprout new <command> -i` 逐条验证输出路径、类型校验与冲突策略。
5. 用 Agent + `sprout-authoring` 执行日常模板调整。
6. 当旧脚本能力完全覆盖后，停用项目特化脚本入口。
